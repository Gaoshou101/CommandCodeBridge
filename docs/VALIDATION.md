### 交付与故障边界

- `GET /models/evidence?credential_id=...` 和模型页选择器：模型观察绑定密钥／更新时间、代理、上游、ZDR、账户及完整模型配置。插件直测、CPA 请求分别展示；24 小时过期，旧无作用域记录不充当新证据；证据随保留日志截断而丢失。普通 403 不推断套餐拒绝，仅明确 `MODEL_NOT_IN_PLAN` 标为不在套餐，429 为临时限流，局部失败不使整张凭证失效。
- 日志新增客户端／上游协议及 ZDR 请求标记。实际 CPA 会把 `SourceFormat` 改为翻译后的插件输入，因此优先使用原始 `request_path` 识别 Responses；本地 13 请求验收对照了该字段。
- 独立变更标记保留 250ms 批量写入；额度更新只写 `usage.json`。每分钟检查点、格式清单、单文件损坏隔离与恢复警告；无检查点只重建该观察文件，设置／未知格式仍失败。缺失主文件可恢复检查点，部分 JSON 解码不会污染恢复值。
- 分层统计保持累计总量，近期分钟／历史 UTC 日；默认不删除日总量，非零保留天数需明确确认。查询重叠整日时返回精度提示。首次迁移、清空均保留副本；清空前检查点被移走，关闭刷盘与 epoch 回归保留。
- 采样保留缓存、错误退避、请求合并和 3 并发，周期增加 0–20% 正抖动。真实个人／组织与同账号多 key 身份未核实，因此没有跨凭据合并查询。

### 本机合成测量

同一次 Windows Go 运行，90 天 × 2 模型 × 每分钟一条请求；固定 259,200 请求、每条 100 输入／20 输出 tokens。只对统计内存结构进行压缩前后对照，不调用上游。测量前两次 GC 排除上次 JSON 缓冲池暂留；不是生产负载与整进程内存承诺。

| 指标 | 压缩前 | 压缩后 |
| --- | ---: | ---: |
| 统计桶 | 259,200 | 21,768 |
| JSON 字节 | 77,241,601 | 6,492,669 |
| 序列化耗时 | 473.612ms | 43.071ms |
| JSON 解码耗时 | 883.126ms | 100.392ms |
| 40 次统计查询 P95 | 90.065ms | 5.033ms |
| GC 后 Go HeapAlloc | 66,310,272B | 5,730,944B |
| 累计请求数 | 259,200 | 259,200 |

压缩耗时 129.314ms；JSON 缩减约 91.6%。这是可重复合成结构测量，解码耗时不是完整 CPA 启动时间。运行：`BRIDGE_MEASURE=1 go test ./internal/bridge -run TestRuntimeScaleMeasurement -v -count=1`。

原生 CPA + 固定模拟 SSE、每轮 32 请求、1,000 条日志缓冲的短样本对照：

| 并发 | 第一轮 requests/s / P95 | 第二轮 requests/s / P95 |
| --- | ---: | ---: |
| 1 | 14.09 / 71.85ms | 14.41 / 84.68ms |
| 8 | 100.67 / 91.57ms | 104.99 / 76.43ms |

两轮均使用同机 Windows CPA v8.0.23 与相同夹具。样本小、有模拟分片等待，单并发 P95 本次变慢，多并发本次变快，不能据此宣称吞吐优化或真实推理变快。分类写入由确定性测试核实：一次纯额度变更，原逻辑写三文件，当前只写一个；检查点首次写入会额外写一次，后续一分钟内不重复刷新。无新增 SQLite／WAL 依赖。

## 持久化优化

原实现每次记录都在服务锁内序列化并写入日志/统计 JSON。当前实现：

- 单个写入任务每 250ms 合并一次变更，无逐请求写入队列。
- 在锁内取得快照，序列化和磁盘写入在服务锁外完成。
- 写入失败保留待写状态并重试，管理状态返回 `storage_error` 与 `storage_pending`。
- 正常卸载先等待活动请求完成，再执行最终刷盘。
- 统计清空与磁盘快照串行，旧快照不能覆盖清空结果；旧请求的日志保留，计数按统计 epoch 处理。

正常刷新间隔为 250ms；强制结束进程或断电可能丢失尚未写入的记录。磁盘故障时不能保证这一时间窗口，错误状态会保留。双 JSON 文件不是跨文件事务。

### 前台记录基准

WSL Linux amd64，Go 1.27.2，i5-12600KF，完整保留缓存，每组 1 秒：

| 日志保留量 | 原实现 | 批量写入 |
| --- | ---: | ---: |
| 1,000 | 2.820ms/op，约 2.10MB 分配/op | 0.522µs/op，约 1.15KB 分配/op |
| 10,000 | 22.853ms/op，约 17.78MB 分配/op | 0.769µs/op，约 1.79KB 分配/op |

这是前台记录调用的开销；新实现将序列化与 IO 转移至后台，不能将此倍率直接当作端到端吞吐提升。

### 实际 CPA 并发基线

`tests/cpa_benchmark.py --requests 64`，同一机器、默认保留 1,000 条，模拟 SSE 固定分片延迟，监听队列 128：

| 并发 | 原请求/秒 | 新请求/秒 | 原 P95 | 新 P95 | 原磁盘写入 | 新磁盘写入 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 18.42 | 20.04 | 57.34ms | 50.87ms | 39.54MB | 8.66MB |
